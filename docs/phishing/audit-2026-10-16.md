# Phishing audit — 16 October 2026

## Status at the start of this audit

The deployed `hybrid-v1` / `forensics-v1` pipeline was not ready for useful general web detection. The user's Google result was an accurate reflection of its restrictive policy, not a successful URL assessment. The previous change prevented an unsupported positive but did not repair model generalisation.

| Finding | Effect | Required improvement |
|---|---|---|
| Primary training had 0 legitimate and 6 phishing HTTPS rows | HTTPS source calibration was unsupported; source benchmark F1 did not establish live accuracy | Representative labelled URLs; scheme-neutral representation and domain-disjoint evaluation |
| BERT also misclassified HTTP Google variants | HTTPS was not the only defect | Quarantine unreliable model output, compare independently trained candidates |
| Policy rejected almost every HTTPS result | Ordinary URLs ended as UNAVAILABLE | Replace blanket scheme gating with an evaluated model plus current observations |
| Collector disabled by default | DNS, TLS, redirects, page forms and registration were not checked | Enable isolated live collection in normal phishing startup |
| Seven named brands and a fixed 75-point forensic alert | Small static coverage; identical scores despite different evidence | Generic destination analysis; learned URL text/structure; recorded evidence contributions |
| Collector selected IPv6 first and discarded oversized pages | Legitimate pages could lose useful observations | Prefer available IPv4, bounded truncation and explicit partial-page coverage |
| Summary repeated errors, internal scheme counts and raw attributions | Confusing user report | One verdict/score, factual findings, check coverage; technical details expandable |
| Previous URL smoke tests had no independent labels | They established contract behaviour, not accuracy | Source-labelled mixed sample, model-only results and external evidence kept separate |

Historical baseline evidence is retained in `models/phishing_url/research/forensics_regression.json`: seven normal HTTPS addresses were withheld and one deceptive userinfo address received a constant forensic score. These results are not claimed as an accuracy benchmark.

## Work and evaluation approach

- Train candidates separately; retain old model files for audit/rollback. No Google/domain safety exceptions are used at inference.
- Use the approved primary corpus plus the official UCI PhiUSIIL URL/label data (1 legitimate, 0 phishing; Prasad & Chandra, CC BY 4.0). Transport scheme is not a model feature. Train, fusion fitting, calibration, alert-threshold selection and test domains remain separated.
- The structure-only candidate was rejected as a standalone replacement: held-out F1 0.6923 and recall 0.5501. It removed challenge homepage alerts but missed too many phishing examples. It is not the deployed detector.
- Evaluate a URL-text + structural ensemble. Its structural development evaluation partition was reused, so source test results alone do not certify deployment accuracy. A separate dated web sample is necessary.
- The unmasked-text ensemble was also rejected: source test F1 0.8763 / recall 0.8123, but it alerted on 5/19 held-out official homepages, including Google and GitHub. This demonstrates why source metrics alone were insufficient. The next representation masks registered-domain identity, retains subdomains/path/query/fragment and uses separately learned structural features. It contains no per-domain verdict exception.
- Collect public DNS, verified TLS, final redirects, bounded static HTML/password forms and RDAP observations dynamically. No JavaScript, credential submission or internal-address fetching.
- Query PhishStats with a hostname only; exact URL comparison happens locally. Cache for 90 minutes and enforce a local daily request budget. No match, outage and provider limits remain distinct from a clean verdict.
- The combined risk index uses the model result and unique observed evidence updates. Evidence weights are versioned policy configuration, not learned probabilities; the final index must not be presented as a percentage certainty. No fixed 75-point output remains.

## External comparison protocol and access limits

The dated random sample is `research/dynamic_web_sample.json` (seed 20261016): eight high-score provider-reported phishing URLs and eight official homepages. These are source labels, not guaranteed present-day ground truth. A reported phishing site may already be offline or may be a provider false positive.

PhishStats's [documented public API](https://phishstats.info/api-docs) was reachable. It allows 50 anonymous requests/day and recommends caching rather than polling more often than its 90-minute refresh. The public service supplies an actual second observation; absence from it does not certify safety. Do not count its reports as independent ground truth when evaluating the same reputation-enriched pipeline.

Eight read-only exact-URL searches were attempted against [urlscan](https://urlscan.io/docs/api/): five returned HTTP 403 and three had no exact report. Other sample rows were deliberately not queried to avoid bulk requests. These rows have no usable urlscan verdict; none was invented or treated as safe. No new public scans were submitted.

[VirusTotal](https://docs.virustotal.com/docs/api-overview) requires an API credential or a signed-in VTAI connection. No authenticated access was available, so no VirusTotal detection counts are claimed.

Google's visible [Safe Browsing status page](https://transparencyreport.google.com/safe-browsing/search?url=google.com) returned **Check a specific URL** for `google.com`, explaining that large sites can contain both safe and unsafe content. The exact-homepage lookup was attempted separately; an unavailable or pending UI result must not be reported as a clean verdict.

OpenPhish was researched but not added as a default runtime dependency because its current community terms restrict organisational/commercial product-development use. Provider availability and usage terms are part of the integration decision.

## Reputation correction and access limits observed

The earlier full-URL substring query missed reports without wildcards and was slow after adding them. The final integration queries the provider's observed indexed `host` field using equality, then performs exact URL matching locally. A generic three-host OR prefetch returned 17 real provider records in one request; all three reviewed positive cases had fresh exact reports. Caller labels never become cache evidence. Provider responses and the daily ledger persist across restarts. The conservative local daily request budget was then reached: uncached lookups are explicitly RATE_LIMITED, while cached observations and the URL model continue. Do not reset the ledger to bypass quota.

The first supplementary path run stopped before dispatch with HTTP 503 because the isolated test server could not bootstrap its Kafka producer. Kafka was subsequently reachable and the rerun completed; shared Kafka/Mongo services were not restarted. Mongo's pre-existing container health check reports unhealthy despite successful result persistence; this audit does not claim repair of that shared infrastructure health check.

## Certificate signatures and path navigation extension

The collector analyses the validated leaf certificate: issuer/subject, validity dates, SHA-256 fingerprint, signature hash/OID, key type/size, negotiated TLS/cipher and weak hash/key flags. OpenSSL's normal handshake validates trust-chain signatures, dates and URL hostname; a failed validation is recorded and never retried insecurely. Revocation, certificate transparency and organisational identity are not verified. A valid certificate is not a benign-site verdict, and short-lived/expiring certificates are not automatically suspicious.

Every successfully observed HTTP hop records URL, status, path and its TLS certificate details (up to three redirects). Forensics catches intermediate HTTPS-to-HTTP transitions and repeated registered-domain changes. Submitted paths are inspected for double encoding/dot segments and explicit navigation parameters. Parameter destinations and arbitrary HTML links are not crawled. Normal SSO redirect parameters are informational. Static password-form actions still receive separate analysis. New certificate/path indicators request review; they do not invent a trained accuracy gain or erase known model false positives.

Live navigation testing found and fixed a collector defect: the default HTTP `Host` header included `:80`, which GitHub copied into `https://github.com:80/`, causing an SSL protocol failure. Default ports are now omitted from Host; explicit non-default ports are preserved. Completed hops and Location targets survive later failures. An optional AAAA lookup timeout no longer discards an available IPv4 answer; only validated/pinned public addresses are contacted, and private answers are still rejected.

Final live controls all passed: Google's valid HTTPS certificate, GitHub's HTTP-to-HTTPS redirect, `expired.badssl.com` expiry rejection and `wrong.host.badssl.com` hostname rejection. Results: `models/phishing_url/research/certificate_navigation_live.json`. These badssl cases are transport-security controls, not labelled phishing examples. Earlier unsuccessful attempts exposed the Host-header defect and intermittent DNS/broker delays; they were not counted as successful checks.

The final authenticated Gateway/Kafka/deployed-worker/Mongo/persisted-report smoke passed, including HTTP 401/403 owner isolation, invalid-scheme rejection and standard score persistence. Google returned **16.2 / LOW** with saved SHA-256 signature metadata and navigation evidence. Result: `models/phishing_url/research/platform_verification.json`. A failed earlier Google attempt retained a numerical score while DNS collection timed out; unavailable collection does not force all HTTPS results to UNAVAILABLE anymore.
